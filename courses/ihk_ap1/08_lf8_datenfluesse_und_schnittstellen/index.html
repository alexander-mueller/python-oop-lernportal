2. HTTP-Statuscodes im Überblick

  • 2xx (Erfolg): 200 OK, 201 Created (nach POST), 204 No Content.
  • 3xx (Umleitung): 301 Moved Permanently, 304 Not Modified (Caching).
  • 4xx (Client-Fehler): 400 Bad Request (Syntaxfehler), 401 Unauthorized (Auth fehlt), 403 Forbidden (Rechte fehlen), 404 Not Found.
  • 5xx (Server-Fehler): 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.

3. JSON Web Tokens (JWT)

Stateless Authentifizierung über einen dreiteiligen String: Header.Payload.Signature.
Der Server signiert die Payload mit seinem geheimen Schlüssel. Clients senden das Token im Header Authorization: Bearer <Token>. Der Server prüft die Signatur mathematisch ohne Datenbankabfrage.

REST-API und HTTP-Methoden 8 Punkte
Ein Ticketsystem stellt eine RESTful-API für Drittanwendungen bereit.

Ordnen Sie die vier grundlegenden CRUD-Operationen (Create, Read, Update, Delete) den entsprechenden HTTP-Verben zu und erklären Sie, was Idempotenz bedeutet.

💡 Offizieller IHK-Erwartungshorizont & Punkteverteilung
CRUD Zuordnung: Create -> POST (oder PUT bei bekannter URI). (1 Pkt.) Read -> GET. (1 Pkt.) Update -> PUT (vollständiges Ersetzen) oder PATCH (partielles Ändern). (2 Pkt.) Delete -> DELETE. (1 Pkt.) Idempotenz: Eine Eigenschaft von HTTP-Methoden, bei der mehrfache identische Anfragen denselben Serverzustand zur Folge haben wie eine einzelne Anfrage. GET, PUT und DELETE sind idempotent; POST ist nicht idempotent (mehrfache Ausführung erzeugt mehrfache Ressourcen). (3 Pkt.)

Bei der Entwicklung einer Schnittstelle treten verschiedene Fehlerfälle auf.

Nennen Sie die Bedeutungen und typischen Anwendungsfälle der folgenden vier HTTP-Statuscodes: 200, 201, 401, 404 und 500.

💡 Offizieller IHK-Erwartungshorizont & Punkteverteilung
1. 200 OK: Anfrage erfolgreich ausgeführt und Nutzdaten geliefert. (2 Pkt.) 2. 201 Created: Neue Ressource wurde erfolgreich angelegt (z. B. nach POST). (2 Pkt.) 3. 401 Unauthorized: Zugriff verweigert, Authentifizierung fehlt oder ist ungültig. (2 Pkt.) 4. 404 Not Found: Die angeforderte URI existiert auf dem Server nicht. (2 Pkt.) 5. 500 Internal Server Error: Unerwarteter Serverfehler bei der Verarbeitung. (2 Pkt.)
Datenformate JSON vs XML 8 Punkte
Eine Schnittstelle soll Datenstrukturen austauschen.

Vergleichen Sie JSON und XML hinsichtlich Syntax-Overhead, Lesbarkeit, Datentypen-Unterstützung und Schema-Validierung.

💡 Offizieller IHK-Erwartungshorizont & Punkteverteilung
Syntax-Overhead & Payload: JSON hat durch schlichte Key-Value-Klammerung { } deutlich weniger Overhead als XML mit seinen redundanten schließenden Tags . (2 Pkt.) Datentypen: JSON unterstützt native Typen (String, Number, Boolean, Array, Null, Object). XML interpretiert alle Werte primär als Text. (2 Pkt.) Schema-Validierung: XML besitzt ausgereifte, standardisierte Validierungsmechanismen über XSD (XML Schema Definition) und DTD; bei JSON ist JSON Schema zwar verfügbar, aber historisch weniger formalisiert. (2 Pkt.) Parsing-Performance: JSON lässt sich nativ in Webtechnologien und modernen Programmiersprachen signifikant schneller und speicherschonender parsen. (2 Pkt.)
API-Authentifizierung JWT Bearer Token 8 Punkte
Der Zugriff auf eine REST-API wird über JSON Web Tokens (JWT) abgesichert.

Beschreiben Sie den dreiteiligen Aufbau eines JWT (Header, Payload, Signature) und erläutern Sie, wie der Server die Integrität prüft, ohne das Token in einer Datenbank nachzuschlagen (Stateless).

💡 Offizieller IHK-Erwartungshorizont & Punkteverteilung
Dreiteiliger Aufbau (durch Punkte getrennt, Base64Url-codiert): 1. Header: Enthält den Token-Typ (JWT) und den verwendeten Hashing-Algorithmus (z. B. HS256 oder RS256). (2 Pkt.) 2. Payload (Claims): Enthält die Nutzdaten (z. B. user_id, rollen, ablaufdatum exp). (2 Pkt.) 3. Signature: Wird erzeugt, indem der codierte Header und Payload mit einem geheimen Serverschlüssel gehasht/signiert werden. (2 Pkt.) Stateless-Prüfung: Der Server benötigt keine Session-Datenbank. Er berechnet aus empfangenem Header und Payload mit seinem geheimen Schlüssel die Signatur neu. Stimmt sie mit der im Token mitgelieferten Signatur überein und ist exp nicht abgelaufen, ist das Token garantiert echt und unverfälscht. (2 Pkt.)
Webhooks vs Polling Architektur 6 Punkte
Ein Ticketsystem soll ein Überwachungs-Dashboard in Echtzeit benachrichtigen, sobald ein Ticket den Status "KRITISCH" erhält.

Vergleichen Sie Webhooks und Polling hinsichtlich Netzwerklast, Latenz und Serverressourcen.

💡 Offizieller IHK-Erwartungshorizont & Punkteverteilung
Polling (Pull-Prinzip): Der Client sendet in festen Intervallen (z. B. alle 10 Sekunden) kontinuierlich HTTP-GET-Anfragen an den Server. Erzeugt enorme Netzwerklast und Serverabfragen, selbst wenn sich stundenlang nichts ändert (leere Antworten); Latenz entspricht dem Polling-Intervall. (3 Pkt.) Webhook (Push-Prinzip): Der Client registriert eine Empfänger-URL beim Server. Sobald das definierte Ereignis eintritt, sendet der Server sofort eine HTTP-POST-Anfrage mit dem JSON-Payload an die URL. Minimale Netzwerklast (Traffic nur bei echten Events) und sofortige Benachrichtigung ohne Latenz. (3 Pkt.)
